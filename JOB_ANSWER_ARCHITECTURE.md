# Job Application Answer Builder — architecture

The `/job-answer` tool. This document is for contributors adding or changing
answer content.

## It is not AI, and the site must never say it is

There is no model behind this tool, no API key, and no network request. It is a
**deterministic composer over a tagged content corpus**: human-written sentence
patterns, selected by tags, filled with the visitor's own words, assembled by a
seeded pseudo-random generator.

Approved wording: *Answer Builder*, *Smart Answer Builder*, *Application Answer
Helper*, *Tailored Answer Draft*, *Suggested Answer*, *Answer Framework*.

Wording that would be false and must not appear: *generated by AI*, *powered by
AI*, *AI-written*.

## The no-fabrication rule

The tool must never assert a fact about the candidate that the candidate did not
supply. This is enforced in three places, and all three are unit-tested:

1. **The corpus contains no digits at all.** No percentages, no currency, no
   team sizes, no timeframes. `src/data/jobAnswers/corpus.test.ts` fails the
   build if a digit appears in any block.
2. **Factual slots prefer prompting blocks.** When the visitor has given nothing
   for a Situation / Task / Action / Result slot, the selector insists on a
   block carrying a `[[…]]` prompt, which renders as a visible bracketed request
   for their own detail.
3. **The visitor's sentences are inserted verbatim** and listed back to them in
   the "Your own facts, kept intact" panel.

So an empty-handed visitor gets a *shape* plus a list of what to supply — never
"I increased revenue by 47%".

## Scale

Measured by `corpusStats()` in `src/lib/career/jobAnswer/index.ts`, and
asserted in the unit tests so it cannot silently shrink:

| | |
|---|---|
| Content blocks (source sentences) | **746** |
| Question categories | 35 |
| Industries | 18 |
| Roles | 75 |
| Skills | 98 |
| Conservative variation floor | **1,720,320** |
| Raw composition space | ~1.6 × 10¹³ |

The conservative floor is the number to trust. It assumes only **four**
eligible blocks survive tag filtering for each slot of a standard-length
answer, across all 35 categories, 4 tones and 3 lengths — and it still clears
the 10,000-variation target by two orders of magnitude. The raw composition
space multiplies out every framework and length recipe before tag filtering,
so it is an upper bound rather than a promise.

Neither figure counts the visitor's own sentences, which are woven in verbatim
and are what actually make two drafts different in practice.

Block counts per file: openings 40, situations 60, tasks 40, actions 70,
results 55, reflections 40, transitions 30, closings 35, motivation 95,
strengths 105, weaknesses 44, goals 28, technical 104.

## Layout

```
src/data/jobAnswers/          the corpus — data only, no logic
  types.ts                    FROZEN CONTRACT: every axis and block shape
  index.ts                    aggregator + corpusCoverageReport()
  categories.ts               35 question types, patterns, frameworks, tips
  industries.ts               18 industries: detection signals + outcome words
  roles.ts                    job titles → industry + seniority
  skills.ts                   skills → detection signals
  openings.ts  situations.ts  tasks.ts  actions.ts  results.ts
  reflections.ts  transitions.ts  closings.ts        behavioural blocks
  motivation.ts  strengths.ts  weaknesses.ts  goals.ts  technical.ts

src/lib/career/jobAnswer/     the engine — logic only, no content
  types.ts                    request/result types
  random.ts                   seeded PRNG (mulberry32 + FNV-1a)
  classify.ts                 question → category
  context.ts                  inputs → industry, seniority, skills, sentences
  select.ts                   tag filter → specificity score → weighted draw
  compose.ts                  recipes, sentence distribution, variants, STAR
  index.ts                    public API: buildAnswer(), classify(), corpusStats()
```

Nothing is one giant file. Adding content means appending to a themed file.

## How a draft is built

1. **Classify** — the question is scored against every category's regex
   patterns and keywords. A specific match always beats the `general` fallback.
   The category decides the default framework and, critically, whether STAR is
   appropriate at all.
2. **Build context** — industry, seniority, role and skills are detected from
   the job title and pasted advert; the notes are split into sentences and the
   ones containing a figure are flagged.
3. **Pick a recipe** — framework + length → an ordered list of block roles.
4. **Distribute the visitor's sentences** across the factual slots, reserving a
   sentence containing a figure for the Result slot.
5. **Select a block per slot** — filter by every tag axis, score by specificity
   (an exact industry match outranks a catch-all), then draw from the top band
   using a seed derived from the inputs plus the variation number.
6. **Render** — `{vars}` are filled from the visitor's data; `[[prompts]]`
   become visible `[brackets]`.

Three variants are produced (best / more concise / alternative angle), each
steering away from blocks the earlier variants used. A STAR breakdown is added
only when the category supports it.

## Variation without randomness

Same inputs + same variation number → byte-identical output, always. Variation
comes from:

- the **variation counter**, bumped by the "Another version" button;
- **recently used block ids**, held in `sessionStorage` (block ids only — no
  personal text) and passed back in as `avoidBlockIds`;
- tone, length and framework changing which blocks are eligible at all.

This is why the engine is testable: tests pass an explicit variation number
instead of stubbing a random source.

## Adding content

**A new sentence** — append a `ContentBlock` to the themed file matching its
role, with a unique id prefixed like its neighbours. Tag it. Absent tag array =
"applies everywhere".

```ts
{
  id: "act-health-triage-04",
  role: "action",
  text: "Rather than escalate straight away, I worked through {skill} with the ward team before changing anything.",
  requires: ["skill"],
  categories: ["problem-solving", "pressure"],
  industries: ["healthcare"],
  seniority: ["mid", "senior"],
  tones: ["professional"],
}
```

Rules: British English, complete sentence, capital start, full stop end, no
digits, at most one `[[prompt]]`, and every `{var}` declared in `requires`.

**A new question type** — add the id to `QUESTION_CATEGORIES` in `types.ts`,
then add a `CategoryDefinition` to `categories.ts` with patterns, tips,
examples, `defaultFramework` and `supportsStar`. Set `supportsStar: false` and
keep `star` out of `allowedFrameworks` for anything that is not behavioural.

**A new industry / role / skill** — append to `industries.ts`, `roles.ts` or
`skills.ts`, then tag blocks with the new industry to specialise their wording.
Skill signals must be at least three characters or they match inside unrelated
words.

**A new tone or length** — extend `TONES` / `ANSWER_LENGTHS` in `types.ts`. The
tag-coverage tests will then fail until every core block role has at least one
block usable with the new value, which is the intended safety net.

**A new framework** — add it to `FRAMEWORKS` in `types.ts` and give it a recipe
in `RECIPES` in `compose.ts` for all three lengths.

Run `npx vitest run src/data/jobAnswers src/lib/career/jobAnswer` after any
content change. `corpusCoverageReport()` reports duplicate ids, undeclared
variables, dangling `conflictsWith` references and empty roles.

## Performance

The corpus is imported only by `src/lib/career/jobAnswer/index.ts`, which the
tool loads with a **dynamic import on first build**. It is therefore absent
from the homepage bundle and from `/job-answer`'s initial JavaScript — it
arrives only when a visitor actually presses "Build my answer".

Pasted job descriptions are scanned up to `MAX_SCAN_CHARS` (20,000) and notes up
to 24 sentences, so a very large paste cannot lock the main thread.

There is **no build step and no generated file**: the corpus is source, so a
normal build produces no large random diffs. There is no server, no database,
and no background worker — deliberately, since none is needed for combinatorial
assembly in the browser.

## Privacy

Question, notes, job description, skills and drafts stay in the browser. The
only thing persisted is a capped list of recently used block ids in
`sessionStorage`, which contains no personal text and clears with the tab.
